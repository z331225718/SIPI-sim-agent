# TP0V R2024b v3 preparation

This is additive and separate from v2. It has no candidate and no formal
record. MATLAB is accepted only through a caller-supplied executable whose
runtime reports exactly `version('-release') == '2024b'`; PATH and Engine
selection are forbidden. Semantic timing is uninstrumented; trace capture is
diagnostic only. A future aggregate requires the two MATLAB runtime identities
to be exact and rejects any Rust case that is not strictly faster.

The clean candidate is `3cb373b0d4c7d33f771179650c8982303f4329a6` (tree
`3b21f44768312987debdb2e18e24671c01005bd3`), with archive SHA-256
`871f4e72011bab82bace724336724125081acf7f91270d61c5d08be19d1c3602` and
`61921280` bytes. It is an empty freeze child of this preparation change; it
does not include a formal report or acceptance claim.

## Frozen comparison contract

TP0V does not inherit the historical corpus count of 303 scalar slots.  It
uses the same frozen final-scalar projection and comparison policy for its two
package cases: the twelve named fields in `METRICS` from
`tools/run_p5_06_original13_fresh_matrix.py`, finite absolute tolerance
`1e-9`, same-sign infinities, and rejected NaNs. Candidate-only diagnostic
fields are recorded separately and cannot make the MATLAB comparison fail or
pass.

The owner-selected D3 policy remains an independent mandatory gate:
`COM_dB`, `ERL_dB`, and a real same-checkpoint `TD_ILN_dB` each require
`0.1 dB`, with no alignment. `FOM_TDILN` and `ICN_mV` are explicitly not
aliases for `TD_ILN_dB`; while TP0V lacks that checkpoint, this gate is
blocked rather than treated as not applicable.

R2024b reads the pinned source through its supported MAT input path. Before
the core executes, the MATLAB harness reloads the generated MAT `parameter`
matrix and publishes its exact shape plus row, column, kind, and value slots.
The upstream `ComSettings.from_xlsx` producer must match that receipt exactly;
any missing, extra, reordered, type, string, or numeric cell fails the bridge.
This is cache-custody evidence only, not a claim that the candidate Rust
workbook loader proves itself.

## Preflight observations

The fresh archive-only diagnostic report at the configured candidate is kept
outside the repository: SHA-256
`a6d1afdb045914c4bf8f99f7e80b892ba42074a35faf915f5afb53893b3626b2`.
It establishes the twelve-field scalar projection and the MAT cache bridge for
both TP0V package cases. The public Rust root route took 0.436 s per case;
the uninstrumented R2024b engine path took 23.117 s and 23.124 s. This is a
preflight observation only, not the required four independent formal replays.

It remains blocked for two explicit reasons. First, all fourteen supplied
original workbook configurations materialize `COMPUTE_TDILN=0`; TP0V therefore
does not produce the real `TD_ILN_dB` checkpoint and D3 cannot be waived or
aliased. Second, paired MATLAB instrumentation is scalar and warning stable,
but raw f64 normal-ERL vector bytes are not identical for TP0V. The first
comparison has equal shapes, with maximum absolute residuals up to
`1.6543612251060553e-24 s` for time, `4.831690603168681e-13 ohm` for
impedance, and `1.49464948745146e-17` for PTDR/gated values. Since the frozen
vector contract is exact f64 bytes with no alignment or tolerance, these are
blockers rather than values to round or normalize.
